# doc-12: Спостережуваність OpenTelemetry, маршрутизація моделей та CI-перевірки

## 1. Трасування викликів через OpenTelemetry та Langfuse

Для наскрізної видимості роботи агентного конвеєра у проєкті налаштовано експорт телеметрії на базі `@opentelemetry/sdk-node` та `@langfuse/otel`. Кожен виклик генерації або пошуку формує ієрархічне дерево спанів (`Span Tree`), де кореневий спан відповідає призначеному для користувача запиту, а дочірні спани фіксують етапи `rag.retrieve`, `rag.rerank_rrf`, `llm.generate` та `verify.check`.

У метаданих кожного спану обов'язково зберігаються назва використаної моделі (`gen_ai.request.model`), фактична кількість вхідних і вихідних токенів, розрахована грошова вартість у доларах США та список ідентифікаторів процитованих фрагментів корпусу. Для локальних запусків без підключення до хмарного сервера Langfuse всі метрики паралельно серіалізуються у локальні JSON- та JSONL-артефакти в каталозі `docs/lab2/` і візуалізуються у вигляді діаграм у `docs/lab2/traces/*.png`.

## 2. Політика маршрутизації моделей за складністю завдання (Model Routing)

Раціональне використання обчислювального бюджету базується на розподілі завдань між моделями різної потужності та вартості:
- Рівень `Tier-0 (Deterministic / Embed)` — детермінований чанкінг, токенізація BM25, RRF-злиття та локальна векторизація моделлю `nomic-embed-text` (`768` вимірів, `$0.00`); виконує `100%` первинної фільтрації корпусу без залучення генеративних LLM.
- Рівень `Tier-1 (Fast Worker / Verifier)` — швидкі компактні моделі `qwen3:4b` або `gemini-2.5-flash`; застосовуються для паралельного прогону еталонного набору у `scripts/parallel-eval.ts` та для незалежної міжмодельної верифікації у `scripts/verify.ts`.
- Рівень `Tier-2 (Reasoning / Synthesis)` — повнорозмірні моделі `qwen3:8b` або `gemini-2.5-pro`; залучаються для складних багатоходових запитів із тегом `hard`, що вимагають синтезу фактів із кількох документів одночасно.

## 3. Автоматизований конвеєр безперервної інтеграції (GitHub Actions CI)

Конфігурація `.github/workflows/ci.yml` запускається на кожен `push` та `pull_request` у гілку `main` і виконує чотири обов'язкові стадії в повністю автономному режимі без доступу до зовнішніх API провайдерів:
1. Перевірка статичної типізації командою `npm run typecheck` (`tsc --noEmit`).
2. Статичний аналіз коду та правил безпеки лінтером `npm run lint` (`eslint .`).
3. Прогін модульних та інтеграційних тестів `npm test` (`vitest run`), який включає офлайн-тести валідатора золотого набору, чанкінгу, детермінованого `fakeEmbedder`, гібридного пошуку BM25+RRF, метрик якості та відмов MCP-сервера.
4. Перевірка виробничої збірки застосунку `npm run build` (`next build`).
